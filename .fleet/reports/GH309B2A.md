threats:
  - Local-disk/profile reader, backups, other OS users: SOLVED by encryption at rest while locked (today: secret readable directly).
  - Same-origin script/XSS, malicious extension: NOT solved — can read decrypted state while unlocked and capture the password at unlock; mitigate only by CSP/dependency hygiene (separate issue), short unlock lifetime, not by storage design.
  - Clipboard persistence/history/sync: NOT solved by encryption; replace default export with an explicit file download plus warning; clipboard only as opt-in with warning.
  - Forgotten passphrase: encryption makes the secret unrecoverable without an export; must be stated in UI before migration.
  - Wallet switch/delete: today the identity leaks across wallets and survives deletion; must be scoped and lifecycle-bound.
  - Reload: today restores plaintext without unlock; target: locked until wallet unlock.
  - Lock: JS strings cannot be zeroized; achievable boundary is dropping all references (store, React state, closures) and asserting none remain reachable via store state.
  - Browser crash mid-migration: localStorage setItem is per-key atomic only; needs digest-guarded, idempotent steps.
options:
  - A volatile/session-only secret, persisted public metadata {commitment, createdAt}: no at-rest secret; every reload loses the secret; legacy secrets need export or are lost. Schema `truerepublic_identity_meta_v1`. Simple, but makes any later canonical use impossible without re-creation and turns migration into forced export-or-lose. Rejected as default; acceptable only as the "never unlock/never migrate" fallback.
  - B separate identity passphrase envelope `truerepublic_identity_vault_v1` {v:1, kdf, salt, iv, ct}: clean key separation, independent of wallets; costs a second secret users will forget, a second unlock UX, and still needs the same primitive. Viable alternative; rejected for UX and recovery burden.
  - C wallet-bound envelope `truerepublic_identity_vault_v1` = map address -> {v:1, alg:"AES-GCM-256", kdf:"PBKDF2-SHA256", iter:600000, salt(16), iv(12), ct, aad:"truerepublic/identity/v1|<address>", createdAt, legacyDigest?}: decrypted at wallet unlock with the in-memory password, cleared on lock/switch/delete. Fresh salt => distinct AES key from the mnemonic record (no key reuse); AAD prevents swapping a wallet ciphertext or another address's record into this slot. Requires extracting encrypt/decrypt/deriveKey into services/custodyEnvelope.ts with optional AAD, WalletService delegating byte-compatibly (existing v2 and legacy payloads must still decrypt) — an explicit reviewed refactor, not silent reuse of private helpers. Coupling: wallet deletion must first offer identity export; no password-change feature exists, so no re-encryption path is needed yet. No custom cryptography in any option.
migration_state_machine:
  - Marker key `truerepublic_identity_migration` {v:1, state, legacyDigest, address?, updatedAt}; legacyDigest = SHA-256 of the raw `identity-store` string. Detection reads the raw string BEFORE zustand hydration (identityStore stops persisting `identity`); nothing is reinterpreted.
  - DETECT: absent -> NONE. Raw > 4 KiB, unparsable, wrong shape/types, missing secret/commitment/nullifier, secret not 64 hex -> QUARANTINED (raw bytes untouched; UI offers raw-text file export only; never decrypted, imported or used). Valid shape but commitment != mockMiMCHash(secret) -> QUARANTINED as "unverified" (never silently repaired). Valid -> PENDING.
  - PENDING: shown as a blocking notice after unlock; user chooses (a) encrypt into the unlocked wallet's vault, (b) export file first, (c) cancel -> stays PENDING, plaintext untouched, notice persists.
  - WRITTEN: one setItem of the envelope; then read-back + decrypt; must equal the parsed legacy record exactly; marker -> VERIFIED with legacyDigest. Any mismatch -> envelope entry removed, plaintext kept, marker ERROR, retry offered.
  - REMOVE: delete `identity-store` only if marker VERIFIED and SHA-256(current raw) == legacyDigest; then marker DONE and a visible "plaintext copy removed after the encrypted copy was verified" notice. Digest differs (another tab/import changed it) -> back to DETECT.
  - Crash/interruption at every step resumes idempotently from marker + stored bytes: before WRITTEN -> PENDING; envelope present but marker not VERIFIED -> re-verify; VERIFIED with plaintext present -> REMOVE. Cross-tab: serialize with navigator.locks ("truerepublic-identity-migration"); without Web Locks, refuse migration (stay PENDING) rather than race.
  - Plaintext is eventually removed only via VERIFIED->REMOVE or explicit user delete after export; QUARANTINED and cancelled PENDING records keep plaintext until a Gio-decided policy (see decisions). No path registers, transforms or submits anything on-chain.
  - Historical vs future: migrated records are labelled "preview (non-canonical, mock commitment)" in vault metadata and UI; GH309C canonical activation generates a NEW identity with the real hash and never promotes a preview record.
